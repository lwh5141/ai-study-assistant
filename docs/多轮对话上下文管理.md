# 多轮对话上下文管理设计说明

> 适用版本:v0.3.1 ｜ 相关代码:`backend/app/routes/chat.py`、`backend/app/services/rag.py`、`backend/app/services/llm.py`、`backend/app/models/models.py`、`src/pages/StudyPage.tsx`

## 一、核心结论

上下文**不依赖 LLM 自身记忆**,而是采用「**数据库持久化 + 每轮重新拼装**」的无状态方案。

会话状态全部存在 SQLite 中;每次提问,后端从库里重新拉取历史 → 截断 → 拼成 `messages` 数组 → 发给无状态的 DeepSeek API。DeepSeek 不保存任何跨请求状态,一切上下文都在请求当下现拼。

整条链路分为五层:存储层、请求编排层、拼装层、生成与来源回传层、前端恢复层。

---

## 二、整体数据流

```
用户提问
   │
   ▼
[前端] 只带 session_id + message + document_ids  (不带历史)
   │  SSE (Accept: text/event-stream)
   ▼
[后端 chat.py]
   1. 复用/新建 ChatSession
   2. 用户消息先落库 commit
   3. 查全量历史 → history[:-1] 排除当前轮
   4. 传 chat_history 给 RAG
   ▼
[rag.py] 混合检索 chunks + 拼装 messages:
   [system 人设] + [历史窗口 chat_history[-20:]] + [当前轮: 资料+问题]
   ▼
[llm.py chat_stream] 整个 messages 发给 DeepSeek,流式返回 token
   ▼
[后端] 流末尾附 <!--SOURCES:...--> → 前端剥离 → AI 回复落库
```

## 三、分层实现

### 3.1 存储层:两张表建模会话（`models.py`）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `ChatSession` | `id` / `title` / `created_at` / `updated_at` | `to_dict()` 实时算出 `message_count` 与首条用户消息的 `preview` |
| `ChatMessage` | `session_id` / `role`(user\|assistant) / `content` / `sources`(JSON) / `created_at` | 外键 `cascade='all, delete-orphan'` 级联删除,按 `session_id` 建索引 |

- 每条 AI 回复的**引用来源 `sources`** 随消息一起持久化,恢复历史时能还原引用角标。
- 一个 `ChatSession` 一对多挂 `ChatMessage`(`lazy='dynamic'`),删除会话时消息级联清理。

### 3.2 请求编排层:先存后取,排除当前轮（`chat.py` → `send_message`）

每次 `/chat` 请求的执行顺序是关键:

1. **有 `session_id` 就复用,没有就新建**会话——标题取用户首句前 30 字(`chat.py:50`)。
2. **先把用户消息落库并 `commit`**(`chat.py:54-61`)。
3. 按 `created_at` **升序查出该 session 全部历史**,再用 `history[:-1]` **切掉最后一条**(即刚存进去的当前提问),避免当前问题重复出现在历史里(`chat.py:73-79`)。
4. 把 `[{role, content}]` 列表作为 `chat_history` 传给 `rag_query`。
5. 流式生成结束后,**再把 AI 回复(含 `sources`)落库**(`chat.py:96-104`)。

> **工程细节**:进入 SSE 生成器前先取出 `sid = session.id`(`chat.py:64`)。因为生成器惰性执行,真正跑 `generate()` 时请求上下文可能已结束、ORM 对象已断开,直接访问 `session.id` 会报错。

### 3.3 拼装层:检索上下文 + 历史窗口截断（`rag.py` → `rag_query`）

发给 LLM 的 `messages` 由三部分组成:

```python
messages = [{'role': 'system', 'content': TUTOR_SYSTEM_PROMPT}]   # ① 导师人设

if chat_history:                                                  # ② 历史窗口(滑动截断)
    for msg in chat_history[-20:]:
        messages.append({'role': msg['role'], 'content': msg['content']})

messages.append({                                                 # ③ 当前轮:资料+问题
    'role': 'user',
    'content': f'【参考资料】\n{context}\n\n【用户问题】\n{question}',
})
```

两个关键设计:

- **历史窗口截断**:`chat_history[-20:]`(`rag.py:64`)只保留**最近 20 条消息**(≈10 个 user/assistant 往返)。目的是控制 token、防止长会话超上下文或成本失控。
- **RAG 上下文不进历史**:检索到的资料 `chunk` 只拼进**当前这一轮的 user 消息**里,不写入历史消息。因此历史轮次只保留纯对话文本——每轮的资料上下文都是**当轮实时检索、当轮注入**,不会在历史里累积膨胀。

### 3.4 生成与来源回传:带内特殊标记（`llm.py` + `rag.py` + `chat.py`）

DeepSeek 无状态,`chat_stream` 只是把整个 `messages` 数组发过去、逐 token 流式返回(最多 3 次重试)。引用来源用一个**带内标记(in-band marker)**回传:

1. `rag.py:79` 在流末尾追加一段标记:`\n<!--SOURCES:{json}-->`。
2. `chat.py:85` 后端转发时一旦检测到 `<!--SOURCES:`,就**停止向前端发送后续 token**。
3. `_extract_sources()` 用正则把 `sources` JSON 剥离出来,**正文与来源分开**保存和返回。

这样一条 SSE 流同时承载了「答案正文」和「结构化引用」,前端无需二次请求。

### 3.5 前端会话恢复层（`StudyPage.tsx`）

- **本地记忆当前会话**:`localStorage` 存 `ai_study_session_id`;页面加载时并行拉取资料列表 + 会话列表,并**自动恢复上次会话**(`StudyPage.tsx:52-67`)。
- **前端不承担上下文责任**:发消息只传 `session_id`,**不传历史**——历史完全由后端从库中重建。
- **新会话 ID 回填**:首次发消息时 `session_id` 为空,`onDone` 回调拿到后端新建的 `session_id` 后回填并写入 `localStorage`(`StudyPage.tsx:159-162`)。
- **侧边栏管理**:支持切换 / 重命名 / 删除会话;切换会话即调 `getSession` 重新拉全量消息渲染。

---

## 四、一句话总结

**「数据库即记忆」的无状态多轮对话**:LLM 不保存任何状态,SQLite 存全量会话。每轮请求后端执行 `先存用户消息 → 查全量历史 → 切掉当前轮 → 滑窗取最近 20 条 → 拼 system+历史+(RAG资料+问题) → 流式生成 → 存 AI 回复`。

优点:简单、可持久化、可跨设备恢复、易调试。

## 五、当前取舍与可优化点

| 现状 | 潜在问题 | 优化方向 |
|---|---|---|
| 固定 `[-20:]` 条数硬截断 | 长会话早期上下文被直接丢弃;不同长度消息 token 差异大 | 改为**按 token 预算截断** |
| 被截断的历史直接丢弃 | 早期关键信息(如用户目标、约束)丢失 | 对被截断部分做**滚动摘要**注入 system |
| 每轮全量查历史 | 超长会话 DB 查询变重 | 限制查询条数 / 分页 |
